# Python Runner 前端体验优化开发文档

> 日期：2026-09-30
>
> 状态：按用户反馈，已撤回第一轮首页布局改造；后续优化必须保留原首页布局。详见 [开发进度](frontend-optimization-progress.md)。
>
> 初始基线：1.5.8+34；本轮发布版本：1.5.9+35。
> 目标平台：Android 手机优先，同时覆盖平板、横屏和分屏。

## 1. 目标与边界

### 本轮确认的统一风格

**保留现有操作习惯，采用 FlClash 那种柔和、克制、有反馈的 Material 3 风格。**

最新界面要求：保留底栏椭圆胶囊、选中背景及全部手势，只去掉胶囊后方的白色全宽矩形背景区域，让页面延伸至胶囊下方。设置、关于及 MCP 设置恢复分组卡片；网络详情不随之改动。列表必须留有可滚动的底部安全余量。

最新澄清：网络页和库管理页必须维持原排版、位置与尺寸。搜索框右侧三个按钮仅增加与搜索框一致的分组背景；库管理的安装行和刷新按钮仅增加同类背景。不得将安装行改成两行、增加安装区标题，或重排筛选标签、统计和列表。这一条优先于文档中其他有关这些页面布局调整的建议。

- 保留原首页布局、导航顺序、页面入口、设置顺序、保存方式和危险操作确认。
- 不新增工具栏、不迁移功能入口、不拆分设置层级，不替换编辑器或终端。
- 优先使用主题表面色形成柔和层次；强调色只用于选中、焦点、状态和主要动作。
- 保持文字层级清晰，不以增大全部字号、增加大圆角卡片或装饰动画代替设计。
- 统一原生控件的按压、焦点、选中、禁用和错误反馈，保留用户主题、字体与动态色偏好。
- 代码和日志保持原有密度与配色策略；普通 UI 的视觉规范不机械套到技术内容。
- 已完成的悬浮底栏手势作为独立组件保留，不给其他页面增加拖动、弹性或无限动画。

本轮实施顺序：公共主题构造与测试 → 设置分组及表单细节 → 通用弹窗与菜单 → 验证主题兼容及原工作流。公共样式会作用于现有原生控件，但不据此宣称所有页面都已完成单独视觉验收。

### 最新约束（2026-10-01，优先于本文其他布局建议）

用户要求首页维持原布局。不得新增第二行工具栏、移动添加/搜索/视图切换入口、更换原标题结构，或重新设计列表、网格及平板详情布局。本方案中与此冲突的建议不再执行。后续仅在原布局内提出细节优化；明显视觉变化须先确认，不直接推广样板设计。

后续明确授权：手机底部导航可参考 FlClash 的 Material 3 样式调整，保留“脚本 / 网络 / 包管理”的入口顺序与行为。此授权不涉及首页内容、顶部栏或平板侧栏。

录屏补充确认：以用户提供的录屏为交互依据，采用悬浮胶囊、按压膨胀、横向拖动预览、松手吸附与随后横向切页，不再以标准 NavigationBar 的点击动画代替。保留三个入口，不照搬参考应用独立的运行按钮；内容区域不启用手动横向翻页。

### 1.1 产品定位

将 Python Runner 打磨为清爽、有辨识度、可信赖的移动 Python 工作台。

- 年轻化：轻快的交互、明确的强调色、干净的图标和易读排版。
- 正式感：统一的组件、稳定的布局、准确的文案和完整的状态反馈。
- 工具属性：优先保障查找脚本、编辑、执行、查看输出和管理依赖的效率。
- 发布品质：暗色模式、长文本、大字体、键盘、异常与低性能设备均可用。

年轻化不等于增加装饰，正式感不等于降低对比度或塞入更多信息。

### 1.2 本轮范围

1. 设计常量、主题、基础组件及全局导航外观。
2. 脚本首页、项目文件页、编辑器、运行控制台。
3. 包管理、设置、运行环境、关于页面。
4. 网络检查、文件选择、更新和诊断页面的规范对齐。
5. 响应式、无障碍、本地化、性能和视觉回归测试。

### 1.3 明确不做

- 不更换 Flutter，不重写编辑器，不引入新的状态管理框架。
- 不以 UI 改造为理由调整数据库结构、运行引擎或 MCP 协议。
- 不替换已有 `re_editor`、`re_highlight` 和 Material 图标体系。
- 不新增登录、云同步、推荐信息流、营销首页等无关功能。
- 不默认引入玻璃效果、大面积渐变、装饰动画或大型字体依赖。
- 不把“前端达到发布品质”等同于应用商店审核通过；签名、隐私、权限和政策合规需另行审核。

## 3. 设计规范

### 3.1 颜色与主题

采用“中性底色 + 一个品牌强调色 + 独立状态色”的结构。

| 角色 | 使用原则 |
| --- | --- |
| 页面底色 | 浅色使用中性灰白，深色使用中性炭黑，不让所有层级都染成蓝灰 |
| 内容表面 | 主要通过轻微明度差区分，避免每层都有阴影和边框 |
| 品牌强调色 | 用于主操作、焦点、当前选中；候选为清晰蓝或青绿，在原型阶段确认 |
| 状态色 | 成功、警告、错误、运行中独立定义，必须同时有文本或图标 |
| 代码颜色 | 优先保证语法对比度，与普通 UI 主题分工明确 |
| 自定义主题 | 使用 `ColorScheme` 推导颜色，不在页面中追加硬编码品牌色 |

最终色值在阶段 A 确认。验收依据不是色值数量，而是层级、辨识度和实测对比度。

- 普通文本对比度目标至少 4.5:1，大文本至少 3:1。
- 必须辨认的图标和控件边界目标至少 3:1。
- 禁用态有明确语义，不用降低整块页面透明度模拟禁用。
- 红色只用于失败或破坏性操作，不作为普通装饰色。

### 3.2 排版

下表为 Flutter 逻辑字号建议，不按屏幕宽度线性缩放。

| 语义 | 建议字号 | 说明 |
| --- | --- | --- |
| 页面标题 | 20–22 | 不使用宣传页式超大标题 |
| 分区标题 | 16 | 中等或半粗字重 |
| 正文、设置主项 | 14–16 | 根据页面密度选定后保持一致 |
| 辅助信息 | 12–13 | 时间、路径摘要、版本等 |
| 紧凑技术信息 | 11–12 | 限日志元数据等场景，不承载主要操作 |
| 代码与终端 | 独立配置 | 保留现有字号偏好和调整能力 |

- 普通中文 UI 使用系统字体或现有 MiSans；代码保留等宽字体。
- 不直接把 `AppTextSize.body` 改大后结束任务，必须逐页检查布局影响。
- 字间距统一为 0；行高以实际中文、英文及混排效果校验。
- 普通内容优先换行，不通过缩小到不可读字号消除溢出。
- 文件列表可省略超长名称，但详情或菜单必须允许查看、复制完整名称。
- 关键错误、权限说明、执行结果不能只显示省略号。

### 3.3 间距与表面

- 沿用 4px 网格；页面水平边距手机默认 16，紧凑工具区可为 12。
- 同组元素间距 8–12，分区间距 20–24。
- 页面分区默认使用无框布局、分组标题和必要的分隔线。
- 卡片仅用于独立重复项、弹窗和确实需要框定的工具，不嵌套卡片。
- 新改造的重复项卡片默认圆角不超过 8；弹窗遵循现有 Material 规范。
- 不批量修改共享圆角常量而让尚未验收的页面全部变化。
- 列表行默认建议最小高度 56，两行信息可为 64–72；大字体时允许增长。
- 图标可为 20–24，但交互命中区域至少 48×48。
- 工具栏、状态区和图标按钮使用稳定约束，加载或状态变化不挤动邻近控件。

### 3.4 控件与动效

- 继续使用 Material 图标，避免同一操作混用多套图标风格。
- 保存、运行、停止、搜索等工具操作优先图标按钮，提供 tooltip 和语义名称。
- 模式使用分段控件或标签页；布尔设置使用开关；颜色使用色板。
- 选项集合使用菜单；数字使用输入框或步进控件，不堆叠文字胶囊按钮。
- 危险操作与普通操作分组，确认弹窗说明具体对象和后果。
- 反馈动效约 120–180ms，页面转场约 180–250ms，以实测流畅为准。
- 遵循系统减少动画偏好；不让转场、缩放或震动成为完成操作的前提。

### 3.5 文案

- 使用短、明确的动作词，例如“运行”“停止”“重试”“复制”。
- 同一概念统一叫法：引擎、Python 版本、项目、脚本、安装目录。
- 不在界面中放设计说明、功能宣传、操作教学或快捷键说明墙。
- 必要状态、错误原因、权限用途和危险操作后果必须保留。
- 技术诊断细节可展开或复制，默认先提供用户能执行的下一步。
- 所有新增文案写入中英文 ARB，通过生成流程更新本地化文件。

## 4. 页面改造任务

### UI-01 全局框架与导航

代码范围：`lib/main.dart`、`lib/ui/app_toolbars.dart`、`lib/ui/app_responsive.dart`。

- 统一 AppBar 标题、操作按钮尺寸、内容边距和滚动分隔线。
- 底部导航保留“脚本 / 网络 / 包管理”，统一选中样式，减少装饰性阴影。
- 设置入口在主要页面保持可发现和位置一致，先核对已有入口再实施。
- 切换页面保留已有滚动位置、筛选和执行状态。
- 平板沿用 NavigationRail；分屏以实际可用宽度判断，不靠设备型号判断。

验收：导航项不会随运行状态位移；重复切换不重置工作内容；返回键行为不变。

### UI-02 脚本首页

代码范围：`lib/features/scripts/presentation/pages/script_list_*.dart`。

- 默认列表突出脚本名，弱化时间、分组等元数据。
- 保留列表/网格偏好，不强制用户改用单一布局。
- 运行入口明确；重命名、导出、删除等低频操作集中于菜单。
- 明确普通、置顶、选中、运行中的视觉区别，不能只靠背景色。
- 搜索、排序、批量选择和拖动排序模式各有清楚的退出入口。
- 搜索匹配数量使用轻量文字，不单独包成抢眼卡片。
- 核对已有最近排序规则；首轮不擅自重命名或增加“最近使用”分区。

必须覆盖：空列表、加载、错误、搜索无结果、长文件名、置顶、运行中、批量选择、拖动排序。

验收：首屏易于找到脚本与运行入口；增加字体后行高合理；运行和编辑不会因点击区域重叠而误触。

### UI-03 项目与文件页

代码范围：`script_project_page.dart`、`project_file_editor_page.dart`，以及 `lib/features/files/`、`lib/pages/app_file_picker_page.dart`。

- 对齐文件和目录图标、名称、次级信息及菜单。
- 当前路径允许长路径换行或横向浏览，不挤压返回和操作按钮。
- 返回上一级、选择文件、浏览文件三个动作语义明确。
- 主程序有明确标记；Linux-like 未就绪时解释原因并提供环境入口。
- 批量移动、删除、重命名复用统一确认和进度样式。

验收：中文/英文长路径、空目录、无权限、取消选择、返回上级均可用；不改变文件操作安全约束。

### UI-04 编辑器

代码范围：`script_editor_page.dart`、`project_file_editor_page.dart`，按需复用现有编辑器组件。

- 代码区域为主体，避免在周围增加装饰卡片。
- 文件名、未保存状态、保存和运行的优先级明确。
- 搜索替换、跳转和其他低频操作保持可发现但不占据大量常驻空间。
- 当前行列和编码等信息仅展示真实可获得的数据，不补造元数据。
- 键盘展开后保持代码光标可见，工具栏不覆盖输入区。
- 同一动作在普通脚本和项目文件编辑器中保持一致。

验收：输入、中文组合输入、选区、撤销重做、保存、返回未保存提示、搜索替换和运行流程不回归；不无关修改 `third_party/re_editor`。

### UI-05 运行控制台

代码范围：`lib/features/console/presentation/`、现有 terminal 组件。

- 清楚区分启动中、运行中、等待输入、成功、失败、已停止。
- 运行中显示停止；结束后显示重新运行，控制位置保持稳定。
- 将关键状态与日志正文分离，不依赖滚动到最后一行判断执行结果。
- 保留 ANSI、复制、自动滚动开关及标准输入能力。
- 长行按既有终端策略横向滚动或可配置换行，不因 UI 统一破坏日志格式。
- 避免加入仅作装饰且无真实动作的桌面窗口按钮。

验收：持续输出时页面可交互；手动向上查看不被强行拉回；等待输入可被识别；退出页面不错误终止或重复启动任务。

### UI-06 包管理

代码范围：`lib/pages/package_manager_page.dart`、`lib/features/packages/`。

- 顶部明确当前引擎，不能把引擎名当 Python 版本。
- 包名、版本和操作区层级清楚，区分已有能力支持的安装状态。
- 安装入口突出，详细安装日志放入专用区域，默认列表不堆叠长日志。
- 安装中、失败、卸载、修复状态使用统一视觉语言。
- requirements.txt、修复等能力受引擎约束时说明原因。

验收：重复点击不会创建重复操作；失败有真实原因和可用动作；界面不提供后端不支持的取消或升级功能。

### UI-07 设置、运行环境与关于

代码范围：`lib/pages/settings_*.dart`、`theme_settings_page.dart`。

保留当前设置分类、排列顺序及所有现有入口，不进行信息架构重排。

- 原位置展示分类、当前值和复杂配置，保留原配置值、存储键、保存按钮及交互方式。
- 去除不必要的分区卡片，使用统一设置行。
- 外观设置保留已有主题与字体偏好；暂不增加更多主题算法选项。
- 运行环境区分“用户选择的引擎”“就绪状态”和“实际执行后端”；发生回退时不能误导用户。
- 关于页区分应用版本、引擎名称、Python 版本和路径信息。
- 版本加载中、未知、未安装属于不同状态；不得使用固定版本或环境名称填充。
- 长路径支持查看完整内容和复制；高级技术信息可展开。

验收：Chaquopy、Linux-like 已安装/未安装、查询失败/超时均有合理展示；从环境设置返回后刷新状态；已有用户偏好保持不变。

### UI-08 网络、诊断、更新与 MCP 辅助页面

代码范围：`network_inspector_*.dart`、`request_override_editor_page.dart`、`app_logs_page.dart`、`update_log_page.dart`、`lib/widgets/`、`lib/features/mcp/presentation/`。

- 网络列表保留方法、地址、状态、耗时等可扫描结构，状态信息不限于颜色。
- 详情标签与复制按钮统一；JSON、请求体、日志不因圆角和内边距损失过多空间。
- 更新弹窗统一版本、进度、失败重试和安装状态。
- MCP 授权明确请求对象、权限和影响范围，不因视觉精简隐藏风险。
- 不改变权限检查、敏感数据遮蔽或确认逻辑。

验收：长 URL、大日志、下载失败、安装失败、授权拒绝、超时均可处理；视觉调整不削弱安全提示。

## 5. 组件与工程实现

### 5.1 复用策略

| 现有位置 | 实施动作 |
| --- | --- |
| `lib/ui/app_design_tokens.dart` | 增补语义字号、尺寸和状态颜色角色，保留迁移期兼容 |
| `lib/main.dart` 中主题构造 | 统一 TextTheme、按钮、输入框、AppBar 和导航主题 |
| `lib/ui/app_surfaces.dart` | 分清独立项卡片与无框分区，按页面逐步迁移 |
| `lib/ui/app_state_views.dart`、`app_empty_state.dart` | 对齐加载、空、失败和重试状态 |
| `lib/ui/app_badges.dart` | 统一少量必要状态标记，避免标签泛滥 |
| `lib/widgets/app_dialogs.dart`、`confirm_dialog.dart` | 对齐危险操作、进度、焦点和键盘行为 |
| `lib/ui/app_toolbars.dart` | 稳定图标按钮命中区、菜单和标题布局 |

只有两个以上实际场景需要相同行为时才提取新组件；不要为视觉改造建立复杂 UI 框架。

### 5.2 状态与数据边界

- 页面消费已有 controller/provider 状态，不复制一套运行状态。
- UI 只展示真实能力和真实数据，不写死版本号、耗时、进度百分比。
- 异步返回检查生命周期；离开页面后不更新已销毁状态。
- 设置返回后的刷新要防止旧请求覆盖新选择。
- 版本等可能启动进程的查询不得放入 `build()`，不得在全局导航切换时重复探测。
- 视觉动画不能阻塞文件操作、执行输出或用户输入。

- 颜色不是唯一的信息通道；焦点顺序合理。

### 7.3 真机与性能

- 至少覆盖一台中低性能 Android 手机和一台平板或可变窗口设备。
- 使用 profile/release 模式测量；记录设备、系统、构建版本、数据量和操作步骤。
- 建议压测：500 个脚本条目、约 5,000 行代码、10,000 行控制台输出；使用合成数据，不含个人内容。
- 首次打开、导航切换、快速滚动、打开编辑器、持续日志输出各记录多次。
- 初始目标：60Hz 场景关键滚动帧的 build/raster P95 各不超过 16.7ms；高刷设备按刷新周期复核。
- 同设备同数据量的耗时和内存若较基线恶化超过 10%，必须分析后决定是否接受；该阈值是告警门槛，不是自动证明合格。
- 不因装饰增加持续动画、重复 blur、大量阴影、无界日志构建或重复异步查询。

### 7.4 端到端必测流程

1. 创建脚本 → 编辑 → 保存 → 运行 → 输入内容 → 查看输出 → 返回。
2. 搜索脚本 → 重命名 → 置顶 → 排序 → 重启应用确认偏好。
3. 打开项目 → 编辑主文件 → 保存 → Linux-like 执行。
4. 安装包成功/失败 → 重试或查看原因 → 返回列表。
5. 切换引擎 → 打开关于页 → 确认真实 Python 版本和环境状态。
6. 未安装 Linux-like → 进入环境页 → 安装或取消 → 返回刷新状态。
7. 修改主题/字体 → 切换所有主要页面 → 重启确认保存。
8. 更新检查失败、文件操作失败、MCP 拒绝授权 → 恢复到可继续操作的页面。

## 8. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 放大字号破坏固定高度 | 普通行改为最小高度并允许增长，工具栏建立稳定约束 |
| 主题统一破坏用户自定义色 | 保留存储键和偏好，使用代表性色值回归 |
| 拆设置页导致值丢失或不刷新 | 保留原保存逻辑，测试进入、取消、返回和重启 |
| 状态展示与后端不一致 | 复用实际状态，不根据 UI 按钮推断成功 |
| 卡片重构影响拖动与点击 | 对排序、长按、滚动和批量选择分别测行为 |
| 大日志、长文件影响性能 | 保留虚拟化和增量更新，避免全量字符串重建 |
| 改导航损害已有使用习惯 | 首轮仅改视觉，结构调整单独验证 |
| 同时修改共享主题与所有页面 | 分阶段提交，每阶段保留可比较截图和可运行版本 |
| golden 在不同环境产生噪音 | 固定 Flutter 版本、字体、语言、尺寸和测试运行环境 |
| Git 忽略工作区文件变更 | 检查 skip-worktree 等标记，确保提交实际包含相关文件 |

## 9. 提交与发布策略

- 推荐按“设计基础 → 首页 → 编辑器/控制台 → 设置/包管理 → 辅助页面 → 验收”拆分提交或 PR。
- 每份变更写明涉及页面、行为是否变化、截图、测试结果和已知限制。
- 不在视觉提交中附带数据库迁移、引擎重构或大规模依赖升级。
- 先内部安装体验，再扩大测试；出现核心流程回归时回退对应阶段，不清空用户数据。
- 发布版本号和更新说明在准备发布时单独处理，本方案不要求提前改版本。
- 新素材须可追溯来源和授权；截图不得包含令牌、私人路径或个人脚本内容。
